Iterating

One change per round

Round Change Macro-F1 (dev)
0 plain instruction + label set 0.33
1 + one example per label 0.46
2 + definitions for B1 vs B2 ?

Every number in that column is measured on dev. It is your steering wheel, not your result.

If you change two things and the score moves, you cannot tell which change caused it.

“Added examples” is not an explanation

Weak

“Round 1: added few-shot examples. F1 went up.”

Strong

“Round 0 confused B1 with B2 on 7 of 14 items. Round 1 added one example of each, chosen from the pool. B1 recall rose 0.29 → 0.57; the B1/B2 confusion halved.”

The second one shows that you read the confusion matrix. That is the skill being assessed.

Use the matrix to choose the next change

evaluate(dev, pred0, ordered=True)     # dev — the half you are allowed to look at

Look at the off-diagonal cells, not only the macro-F1:

  • Most confused pair — which two labels?
  • Adjacent (B1↔︎B2) — a calibration problem on an ordered scale; often fixable with clearer definitions or anchor examples.
  • Distant (A1↔︎C2) — the model is reading the prompt differently from how you intended.

Plain vs. weighted κ

Cohen's kappa            0.200
Cohen's kappa (weighted) 0.871   <- labels are ordered
  scale order used: A1 < A2 < B1 < B2 < C1 < C2

A large difference like this means: the model is usually one level away, and rarely exactly correct.

That is a different finding from “the model performs badly”, and only weighted κ shows it.

But only when the labels are a scale

ordered=True is right for A1 < A2 < … < C2 and Move 1 < 2 < 3.

It is wrong for error categories — Grammatical is not “closer to” Lexical than to Mechanical.

And watch the order

Low/Mid/High is ordered but not alphabetical. Pass it yourself:

evaluate(dev, pred, ordered=True, labels=["Low", "Mid", "High"])

Otherwise the scale is High < Low < Mid and the number cannot be interpreted. evaluate prints the order it used — read that line.

05_test — the held-out run

Commit first, then open it

Fill this in before the next cell runs:

CANDIDATES = {                                  # every prompt you will test
    "v1 few-shot": ROOT / "prompts" / (TRACK + ".txt"),
}
WINNER_RULE = "highest macro-F1; ties go to the simpler prompt"

You may test more than one prompt. That is legitimate — but it is a different claim from testing one, and the difference is entirely whether you said so in advance.

Then run it, once

test = load_gold(TEST_PATH)          # the first time this file is opened all week

freeze_test_run(load_prompt(CANDIDATES[name]), test, f1_by_round, ...)

freeze_test_run runs the prompt, saves before scoring anything, reads that file back off disk, scores those predictions, and appends one line to a log that travels in your submission.

Report every number you tested, not the best one

Three prompts tested and the best reported is the best of three tries, optimistic by an amount nobody can work out afterwards. All three go in report §3.

Nothing stops you running it twice

Stopping you would be the wrong design — a real mistake at four o’clock needs a way forward.

So instead nothing is overwritten: a second run lands in ..._predictions_attempt2.json beside the first, and both stay.

Every scoring appends a line to ..._test_log.jsonl, fingerprinted with the prompt that produced it. Same fingerprint twice = one prompt run twice. Different fingerprints = a prompt changed after seeing the held-out set — and report §5 has to say which happened.
